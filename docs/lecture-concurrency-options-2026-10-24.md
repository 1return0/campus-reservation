# 讲座同步预约：行锁替代方案实测

日期：2026-10-24。基线提交：`0d68edc`。

结论：当前证据更支持“原子扣减成功路径 + 精简事务内 SQL + 售罄路径保留协调锁”作为下一步的小范围候选。仅把前置 `SELECT FOR UPDATE` 换成原子 UPDATE 没有明确收益，不能称为无锁预约。名额分桶／票券化本轮未实现、未验证，不能声称其性能或正确性已经通过。

正式业务源码、正式限流配置、运行中的应用和业务数据库均未调整。实验代码位于独立 detached worktree；主仓库只新增本报告与脱敏结果 JSON。没有提交或推送。

## 条件与方案

- Windows 上独立 Gateway `18600` → 独立 Reservation 测试 JVM `18602` → 虚拟机 MySQL **8.0.45**。JDK 17，Gateway/Reservation 堆上限各 512 MiB，Hikari 10 连接。
- 每个场景固定 **500 笔不同学生的新预约**；客户端并发档 **50、500**；同一讲座名额分别为 **20、500**。每个进程先以 150 笔请求预热。
- Redis 缓存、Redis 准入、消息发布、过期及自动爽约任务全部关闭。HTTP 经 Gateway/JWT 校验；使用测试签发的 JWT，没有执行注册/登录流程。Outbox 验证到数据库落库，不包含 RabbitMQ/Consumer。
- 使用独立新建 `campus_audit_*` schema，Flyway 初始化。四轮结束均清理各自测试库，测试 Gateway 已停止。
- 测试时钟固定为 2026-10-24 09:00（Asia/Shanghai），使用日期固定为 2026-10-25。负载种子 SQL 与剔除 JWT 后的请求 hash 在各方案之间一致。测试行真实创建时间不是冻结的供应商/数据库时钟快照。
- 执行顺序：原版 A1 → 原子扣减 B → 精简版 C → 原版 A2。候选各一轮，原版两轮；不是多轮统计显著性结论。

| 方案 | 实验改动 |
| --- | --- |
| A 原版 | 场次 FOR UPDATE → fresh replay → 有效预约查询 → PENDING 插入 → 扣减/状态更新 → 查询最终单 → Outbox |
| B 原子扣减 | 先条件 UPDATE（同时检查 OPEN、未开始、有余量）；成功后读取场次；失败后仍锁场次复查，协调候补、取消及维护；其余保持原流程 |
| C 原子扣减 + 精简 | 沿用 B 的成功/售罄分支；以联合唯一约束替代重复有效预约 SELECT；直接插入最终 CONFIRMED/WAITLISTED 状态，省去 PENDING→最终状态 UPDATE；售罄锁内已确认零余量时不重复扣减 |

B/C 的并发幂等重放若已经先行扣减，拿到 fresh replay 后在同一事务归还本次多扣的名额。不同幂等键争抢同一用户有效预约时依靠唯一约束拒绝，整笔事务回滚。其余数据库异常同样回滚，未分离提交 Outbox。

所有方案均在 Performance Schema 采样中观测到 `resource_slot/PRIMARY` 等待，峰值 9 个等待连接。这与连接池上限 10、热点场次一次只有一个写事务推进相符。B 的等待主要转移到 UPDATE，C 仍有单库存行竞争。500 名额的 C 场景没有显式场次锁 SELECT；20 名额时有 480 次售罄路径的场次锁 SELECT。

因此收益的明确结构性证据是 SQL 从 9→7、10.92→8.92，以及锁内工作减少；不能把收益全部归因于删除 SELECT FOR UPDATE，也不能声称 C 已消除热点串行。

## 正确性与失败记录

讲座范围内，每个方案的实际 MySQL/HTTP 检查包含：

1. 有充足名额时同一幂等键 20 并发：全部返回 200，只创建一单、一事件、扣一个名额。
2. 同一用户不同幂等键 20 并发：一笔成功，其余业务 409，只扣一个名额。
3. 取消与新请求并发：已有队首候补优先确认。
4. 一名额场景同键并发重放。
5. 顺序取消补位 FIFO。
6. 管理员维护取消全部有效预约。
7. 注入 Outbox INSERT 异常：HTTP 500、事务 doRollback、没有残留预约/Outbox。
8. 管理员维护与新预约并发：维护后无有效预约，初始/取消事件数量匹配。

B、C、A2 的上述检查各 **8/8 通过**。此外，在实验开关关闭时执行原有 `ReservationServiceImplTest`、`SlotCancellationServiceImplTest`、`BookingReplayAndPromotionTest`，共 **22 项单元回归通过**；这不等于候选版本已完成全部生产验收。

初始 A1 复用了更宽的原回归脚本，**16 项中有 1 项失败**：`maintenance-vs-new-booking-room`。20 个研讨室预约请求与关闭窗口并发，创建了 8 笔预约，最终全部失效，但 Outbox 总计只有 8 条而非期望 16 条；维护 HTTP 200。该失败发生在讲座基线分支，实验未改研讨室代码。后续测试明确限定讲座，未将这次失败宣称通过。

代码审查的疑点：研讨室维护入口使用默认事务隔离级别，先普通读取窗口，再等待房间锁；取得锁后 current read 能读到新预约，而普通成员快照查询可能仍使用旧 RR 快照，导致取消通知缺少接收人。此处是待单独复现定位的归因，不是本轮已经修复的结果。失败证据已完整保存在 JSON 的 `initialBroadRun` 中。

## 建议与边界

- 优先将 C 整理为可审查的最小生产改动，再针对剩余风险补测；保留同步响应及同事务 Outbox，幂等、维护、FIFO 作为验收条件。
- 不推荐为了面试表述直接删除所有场次协调锁。候补及维护协议未重新设计前，这样做有竞态风险。
- C 适合小范围减少延迟，但本轮 500 并发批次仍需约 4.83/6.24 秒，不支持“瞬间完成 500 笔”或任意高吞吐声明。
- 若目标是进一步拆除单库存行热点，下一步才是库存分桶／票券化，需要一起设计管理员互斥、候补优先与取消返还；本轮未验证，不能以理论并行度冒充实测提升。
- 共享虚拟机和本地主机，未独占硬件、未做候选多轮统计检验，已有原版波动；不能把这里的改善幅度直接写成生产指标。
- Redis/MQ 宕机、多实例 Reservation、Publisher/Consumer 恢复不在本轮范围。
