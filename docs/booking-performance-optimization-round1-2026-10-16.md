# CampusReserve 第一轮最小优化与对照验收

日期：2026-10-16。基线为 `e1cf801debf6fa485bb7a1eb7297971468155f17` 的上一轮审计；优化代码在本地工作区，未提交、未推送 GitHub。

## 本轮范围

仅修复并发幂等重放、数据库异常状态码，以及研讨室候补成员/占用查询放大。未修改 Redis 配置和限流阈值、数据库表、唯一键、Outbox/Inbox 核心事务逻辑；未引入预扣、MQ 异步预约、新锁服务或新的数据库锁方案。

## 根因、修复与代价

### 并发同键请求偶发 409

原链路：请求 A/B 的首次幂等 SELECT 均返回空 → B 等待既有 slot/room/team 锁 → A 提交 → B 继续。

- MyBatis SESSION 一级缓存可能保留此前的空结果，重复调用相同查询并不等于重新查数据库。
- 讲座 `reserve()` 原来使用默认隔离级别，环境为 MySQL REPEATABLE READ；首次普通 SELECT 建立的旧快照也可能看不到 A 的提交。
- **更正上一轮根因表述的范围**：研讨室 `book()` 原本就显式 READ_COMMITTED，不能把它的故障也全部归因于 RR。对它而言，缓存的空结果已经足以造成拿到队伍锁后仍报 `study-team-already-booked`。

本轮：

- 新增 `findReplayFresh()` 普通 SELECT，`@Options(flushCache=TRUE, useCache=false)`，拿到原有锁后复查；不新增 `FOR UPDATE`、不全局关闭一级缓存。
- `useCache=false` 不能单独解释为禁用一级缓存；这里同时通过 flush 及独立 Mapper 语句保证复查不复用早先的 miss。
- 讲座仅 `reserve()` 改为 READ_COMMITTED；slot 行锁、条件扣容量 SQL、两组唯一约束均保留。先拿锁并复查已存在结果，再验证新预约的时段状态，避免维护后把已提交请求的重放误作新预约。
- 研讨室保留 `book()` 原有 RC；调用批量补位的取消、人工爽约、自动爽约入口也局部使用 RC，使批量成员/占用读不沿用等锁前的旧快照。没有修改数据库全局隔离级别。
- 不同幂等键仍经过原有有效预约/队伍状态约束；研讨室复用同键但改参数仍由原有 `replay()` 校验拒绝。

代价：原先错误地命中本地空缓存的复查现在真正访问 MySQL。普通新预约每请求多约 1 条实际 SELECT，讲座平均实际 SQL 从 9.92 到 10.92，单研讨室从 13.012 到 14.012。这是正确性修复成本，不能假装普通热点吞吐必然提高。

### 数据库异常回滚后返回 403

原来的共享 Advice 没有 DataAccessException 对应映射。未处理的持久层异常会离开正常 MVC 返回链路，进入容器错误转发，再受到 Security 边界影响，最终表现为 403。上一轮注入数据库错误、确认事务回滚后的实际 HTTP 403，以及本轮同场景 500 的对照支持该定位。

新增仅作用于 Reservation Controller 包的 `ReservationDataAccessExceptionHandler`，把 DataAccessException 映射为：

```json
{"code":500,"message":"internal-server-error","data":null}
```

服务事务先因异常回滚，Controller 边界随后生成响应。未放开 `/error` 或 ERROR dispatch，没有改 JWT/角色规则；没有用笼统的 Exception 捕获器吞掉权限错误。日志仅记录异常类型与现有请求关联 ID，不输出原 SQL、参数、驱动错误详情或凭据。

### 候补 N+1

保留 `waiting(... ORDER BY created_at,id FOR UPDATE)` 及已有开放窗口/房间重叠的 current read。新流程：

1. 按原 FIFO 顺序读完整队列。方法内按 `(startsAt,endsAt)` 去重开放窗口、既有占用判断；不截断、不 SKIP LOCKED。
2. 房间已经冲突的候补不必加载成员，避免给最常见同区间队列增加无效批量 SQL。
3. 对可能补位的候补，以最多 **200 个 booking_id/批**读取成员快照，以及通过成员→bucket JOIN 查询冲突预约 ID。参数分批不意味着只处理前 200 个。
4. 按原候补顺序评估。每次成功补位后更新本次扫描的房间区间与成员占用视图，避免第二个候补被先前的批量读误判为空闲；区间仍按 `[start,end)` 判断，首尾相接不冲突。
5. 仍逐条执行原 bucket 唯一键 INSERT、状态条件 UPDATE、同事务 Outbox。跨房间竞争在批量读后发生时，唯一键仍是最终裁决；冲突不吞掉、不提交半成品，沿用整笔回滚语义。

**没有消除所有与队列长度有关的工作**：完整队列仍加载/遍历；不同时间区间的窗口和房间判断仍可能执行 O(U) 条 SQL。仅成员冲突这条约 2N 的数据库往返被批量化。200 参数上限也不是整个请求的内存上限。

隔离真实 MySQL `safety` 补跑 13 项全部通过：

| 场景 | 关键核验 |
|---|---|
| 讲座/研讨室同键并发各 20 请求 | 各 20 个 200，仅 1 预约、1 Outbox；此前各 11 个 200、9 个 409 |
| 两类业务取消与递补 | 最早合格候补确认，后续候补仍等待；3 初始事件 + 取消/递补 2 事件 |

| 混合候补 | 队首成员冲突仍候补；第二个合格候补先确认；与其重叠者不确认；相邻区间可确认 |
| 跨房间竞争 | 5 对共享成员同时预约不同房间：5 确认、5 个业务 409，5 Outbox、20 bucket |

| 递补 Outbox 失败 | 在 bucket 已插入、候补已更新后使事件插入失败；原取消也一并回滚，原单仍确认、候补仍等待、原 bucket 恢复 |

这些是选定场景验证，不等于任意交错、多实例、数据库故障恢复的完整证明。注入的 500 和跨房间业务 409 是预期故障/冲突测试，不是普通压测错误率。

## 性能对照

### 条件与口径

沿用上一轮相同脚本、工作负载、测试探针与分级顺序：Gateway 18600 → 独立 Reservation JVM 18602，JDK 17、堆上限 512MiB、Hikari 10 连接、虚拟机 MySQL 8.0.45；Redis 缓存和两种准入限流均关闭。各并发档 500 请求，固定讲座容量 20，研讨室单房间同区间/12 房间分散；复杂候补仍是 0/50/200/500 深度，每档 3 请求，再加 200 深度、10 并发、30 请求。

基线原始目录 `target/booking-audit-f0d1fdbcb858`；本轮 `target/booking-audit-1f3023a7b7b2`。对齐性能主体 **24 场景、5566 请求**，另有预热和正确性测试。完整 runner 本轮正常结束，JUnit 1 项通过，内部 13 项正确性检查全部通过。独立测试库已删除，测试端口已停止。

TPS 是包含 CONFIRMED 与合法 WAITLISTED 的完成 HTTP 请求数/秒，不是成功占座数/秒。所有性能主体场景 **0 限流拒绝、0 意外 4xx/5xx、0 传输失败**；每次写入均校验新增预约数和新增 Outbox 数相等。没有容量负数或已确认房间预约重叠。

共享物理虚拟机、顺序单轮测试；未独占硬件，也没有多轮随机化置信区间。比较条件一致不等于环境噪声为零。3 样本档位的 P95/P99 等于最大值，仅支撑结构性诊断，不是生产 SLA。

## 剩余瓶颈与后续边界

- 同一资源的持锁事务仍串行，500 在途的大部分请求仍要排连接池或上游队列；本轮不以扩连接池或低限流掩盖问题。
- 大量互不相同区间且已被房间占用的候补，仍有窗口/区间检查 SQL；本轮没有替换这些 current read，不能宣称 N+1 在所有分支都消失。
- 对并发释放导致的资格变化，批量结果仍只是该次读时的资格判断；跨房间新占用由既有 bucket 唯一键裁决。本轮保持“按原顺序选择当次合格候补”的规则，不承诺跨房间变化瞬间的全局线性化公平。
- 尚未做任意故障点、多 Reservation 实例的长时间稳态压测；RabbitMQ 投递/消费未计入本轮性能延迟。
- 未改正式 Redis、表结构或唯一约束，未自动推送。回滚应只逆向应用本轮列出的源码改动，不要 reset 用户其他未提交工作或删除上一轮审计资料。
