# 讲座与研讨室预约写入压测（2026-10-16）

## 结论

当前数据库约束在本次选定负载下保持正确，但同一场次/房间存在明显的热点排队。500 并发突发下，讲座热点 P95 为 6.34 秒，研讨室热点 P95 为 8.76 秒；分散到 12 间房时为 2.63 秒。随后完成的 Redis 准入对照准确放行 20 次、拒绝 480 次，减少进入业务事务的请求；500 并发下获准请求 P95 分别为 0.79 秒与 0.96 秒。应优先配置已有准入保护，没有证据要求立即改为 Redis 库存预扣。

压测工作只新增测试脚本和报告，并按明确授权将 VM Redis 连接参数写入 Git 忽略的 `deploy/.env`；未为追求指标修改预约事务或数据库约束，也没有永久开启/调节本地业务限流开关。用户另外要求的讲座候补普通 `FOR UPDATE` 改动在限流对照前已完成；这些负载只创建预约，不取消或触发讲座递补，因此未执行该候补领取 SQL。Redis 凭据不进入报告或 Git。

## 测试范围与方法

- 本地 Windows：Node.js 22.13.0 负载生成器、单 Gateway、单 Reservation；Java 17，两个 JVM 各 `-Xms256m -Xmx512m`。
- 真实 VM MySQL 8.0.45，`REPEATABLE-READ`，`max_connections=151`，`innodb_lock_wait_timeout=50`。
- 限流对照时只读确认 VM 为 Linux 3.10.0-1160.el7.x86_64、4 个逻辑 CPU、约 7802 MiB 内存，MySQL 与 Redis 共用该 VM。
- 通过 Gateway HTTP 及两层 JWT 验证调用真实 Controller、Service、MyBatis 和 MySQL 事务，不是 Mock。
- 使用服务签名密钥签发合成 STUDENT JWT，研讨室预置一人且已接受的队伍；**不包含登录、注册、组队接口的耗时或校园身份核验**。
- 每个用例使用独立资源、订单、成员、幂等键及 Outbox。基线关闭 Redis 缓存/准入、Outbox 投递、定时关闭和自动爽约；日志 INFO。Hikari 未另行调大，使用框架默认连接池设置。
- 每个用例 500 个不同请求，最大在途并发分别为 50、100、500；闭环发压，没有客户端自动重试。500 并发不是 500 请求/秒，更不是 500 笔全部确认成功。
- 每个场次容量 20；每间研讨室请求同一 `14:00–16:00` 区间，成员互不重复；分散场景轮流请求 12 间房。
- 同一组进程先执行 10 次讲座预热写入，不计入结果；各配置测量一轮，运行顺序和 JIT/系统波动可能影响比较。不提供置信区间或生产容量上限。
- VM CPU/内存及宿主机其他负载未做隔离；本次结果只适用于该开发验证环境。

## Redis 准入对照（已完成）

相同 HTTP 业务入口、单实例和独立合成数据；每用例仍发 500 个不同请求。Redis 缓存保持关闭，只开启两个已有 Lua 准入器。为固定一次突发内准入总数，采用 **60 秒固定窗口、每场次或房间日期最多准入 20 次**。每用户均只发一次，不触发用户维度阈值。

| 场景 | 最大在途并发 | HTTP 200 / 429 | 200 请求 P95（ms） | 429 请求 P95（ms） | 全部响应 P95（ms） | 确认 / 候补 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 讲座热点限流 | 100 | 20 / 480 | 918.07 | 783.38 | 791.08 | 20 / 0 |
| 研讨室热点限流 | 100 | 20 / 480 | 1620.98 | 1390.23 | 1416.08 | 1 / 19 |
| 讲座热点限流 | 500 | 20 / 480 | 788.75 | 1572.38 | 1572.16 | 20 / 0 |
| 研讨室热点限流 | 500 | 20 / 480 | 957.49 | 1435.33 | 1435.02 | 1 / 19 |

原始结果：[booking-write-limited-2026-10-16.json](benchmarks/booking-write-limited-2026-10-16.json)。4 个正式用例合计 2000 次请求：80 次获准、1920 次 HTTP 429，未观察到 HTTP 5xx 或客户端超时；各用例均核对订单、容量/房间重叠、成员 bucket 和 Outbox 一致。

此实验说明 **拒绝过载请求可以减轻热点预约事务的排队**，不是同样 500 笔预约全部完成后的性能提升。限流前后的实际业务工作量不同；获准请求每用例仅 20 个，分位数样本较小。全部响应包含 96% 的拒绝，不能把 279/316 等响应完成速率写成预约成功 QPS，也不据此给出生产吞吐提升百分比。

这也不是持续流量测试。60 秒/20 次仅用于控制变量，不能证明生产配置为 20 次/秒时的长期吞吐或用户重试体验。限流仍在幂等查询之后，所以 HTTP 429 不等于完全没有访问 MySQL。

限流阶段记录的 MySQL 全局锁等待次数每用例为 19，累计锁等待时间约 4.3～7.5 秒；它们是共享服务器全局差值，可能包含其他连接，不能作为每条 HTTP 请求的精确锁耗时。

## 正确性核对与清理

每个用例从 MySQL 核对，而非仅检查 HTTP 状态：

- 讲座：确认数 20、余量 0、候补订单 480、WAITING 条目 480；无同一用户重复有效预约；Outbox 行数等于订单数。
- 单房间：确认 1、候补 499；无两笔 CONFIRMED 房间区间重叠；仅确认预约拥有 4 条成员半小时 bucket；Outbox 行数等于订单数。
- 12 房间：确认 12、候补 488；区间重叠数 0，成员 bucket 合计 48；Outbox 行数等于订单数。
- 所有用例独立成员，所以**不把本轮测试说成验证了同一成员跨房间竞争**，该边界由既有唯一键及单独测试负责。
- 基线与限流对照都按本轮生成的资源/队伍 ID 清理测试订单、候补、成员、bucket、Outbox、窗口和资源，并核对资源与队伍残留为 0。没有删除原有业务数据。Redis 准入键使用本轮独立资源/合成用户，保留不超过 60 秒后自然过期，不执行 FLUSHDB 或删除其他键。

未启动 Scheduler/Consumer，所以没有产生测试通知；本轮不验证 RabbitMQ、Inbox 或端到端通知送达。

## 是否需要优化

1. **需要热点保护，但不建议先重写一致性方案。** 单热点的请求完成速率在数十次/秒量级，500 在途请求主要增加等待时间。已有 Lua 准入已通过真实 HTTP/MySQL 对照验证；下一步是按实际可接受延迟选择每秒阈值并做持续流量测试，而不是把实验用 60 秒/20 次直接当作生产设置。
2. **不要盲目调大 Hikari。** 持有热点行锁的事务仍然只能先后执行，更多连接可能只是把等待从连接池搬进数据库。当前 HTTP 结果无法精确拆分连接池、Tomcat 和数据库锁等待，需要额外观测后才可做归因与调参。
3. **研讨室递补扫描值得进一步分析。** 新预约会先调用 `promoteWaiting()` 扫描已有候补；候补规模增大时有潜在额外开销。但本轮没有 SQL 计数/剖析证据，不能宣称已经证明 N+1 或已定位唯一瓶颈。
4. 若限流后业务仍要求同一房间更高吞吐，再单独评估房间日期/占用刻度粒度的锁方案，并同时覆盖取消、窗口维护和递补路径。不能只替换预约入口就宣布正确。

## 重复运行

先从根 POM 打包当前 Gateway 与 Reservation（及依赖），确保 `deploy/.env` 的 MySQL/JWT 配置正确。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/benchmark/booking-write.ps1 `
  -Mode baseline -Requests 500 -Concurrency '50,100,500'
```

较小开发验证可使用默认 120 请求及 10/50/100 并发，或 `-Repeats 2` 做重复观察。它是轻量闭环 HTTP 负载工具，不冒称 JMeter 报告。

限流对照复现：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/benchmark/booking-write.ps1 `
  -Mode limited -Concurrency '100,500'
```

需要 `.env` 中已有正确的 `RESERVATION_REDIS_HOST/PORT/PASSWORD`。每个并发级别对两种业务分别发送 500 次请求，设置 60 秒固定窗口只准入 20 次，以核对 HTTP 429、实际落库数及预约不变量。**60 秒/20 次是控制变量实验设置，不是推荐的生产限流策略。**

新版脚本额外记录 MySQL 全局锁等待计数差值；本次已归档的基线运行早于这一诊断项，因此原始基线没有该字段。全局差值可能混入其他连接，不等于逐请求分布式 Trace。

## 不可据此宣称

- 多 Reservation 实例、生产 SLA 或稳态最大 QPS 已验证；
- 500 人都成功取得名额，或压测期间“没有排队”；
- 同样 500 笔订单全部落库的 QPS 或延迟获得某个提升百分比；
- RabbitMQ 故障恢复、通知消费和真实校园账号已验证。
